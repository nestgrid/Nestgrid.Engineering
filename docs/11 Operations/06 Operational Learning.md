# Operational Learning

> Part of the **[Operations](README.md)**.

## Purpose

Operational learning turns production experience into better software, documentation and engineering practices.

It ensures that real-world behaviour improves future decisions.

## Guidance

Production teaches teams things that design and testing cannot fully reveal.

Operational learning should feed back into discovery, architecture, testing, deployment and documentation.

### Learn from Incidents

Incidents should produce useful learning.

Follow-up work may include code changes, monitoring improvements, documentation updates, test coverage or process changes.

### Learn from Support

Repeated support questions can reveal usability, documentation or reliability problems.

Support patterns should be reviewed as signals, not only handled as individual tickets.

### Learn from Usage

Actual usage may differ from assumptions.

Usage data and stakeholder feedback should inform future prioritisation and design.

### Update Documentation

Operational discoveries should be reflected in relevant documentation.

Runbooks, decisions, architecture notes and troubleshooting guidance should remain current.

### Close the Feedback Loop

Learning should result in action where action is justified.

Without follow-through, operational learning becomes observation without improvement.

## Key Takeaways

- Production experience should improve engineering practice.
- Incidents should lead to useful follow-up.
- Support patterns can reveal system problems.
- Usage may challenge assumptions.
- Documentation should reflect operational learning.
- Learning requires follow-through.
