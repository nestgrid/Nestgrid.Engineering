# Naming Standards

> Part of the **[Language](README.md)**.

## Purpose

Naming standards define how important concepts should be named consistently across documentation, models, code and supporting artefacts.

Good naming makes systems easier to understand, discuss, maintain and evolve.

## Guidance

Names should communicate intent. A good name helps readers understand what something represents, why it exists and how it relates to the domain.

Naming should be treated as part of design, not as a cosmetic detail.

### Prefer Meaning Over Brevity

Names should be clear before they are short.

Abbreviations, acronyms and shortened names should only be used when they are widely understood and unlikely to cause confusion.

### Align with Domain Language

Names should reflect the shared language of the domain wherever practical.

When a domain term exists, engineers should avoid replacing it with a technical synonym that weakens business meaning.

### Use One Name per Concept

The same concept should not be given multiple names without a clear reason.

Multiple names for the same idea create confusion in documents, models, tests, APIs and code.

### Avoid Overloaded Terms

A single term should not be used for multiple distinct concepts.

If a word has different meanings in different contexts, the names should make those differences visible.

### Name for the Reader

Names should support the person who needs to understand the system later.

The best name is not always the one that was fastest to write. It is the one that makes future understanding easier.

## Key Takeaways

- Naming is part of engineering design.
- Names should communicate meaning clearly.
- Domain language should guide naming where practical.
- One concept should usually have one name.
- Overloaded or ambiguous terms should be avoided.
- Names should serve future readers and maintainers.
