# Glossary

> Part of the **[Language](README.md)**.

## Purpose

The glossary captures important terms, definitions and distinctions used throughout an engineering effort.

It provides a shared reference that supports discovery, domain modelling, architecture, implementation, testing and documentation.

## Guidance

A glossary should be practical, clear and actively maintained. It should focus on terms that affect understanding, decisions or behaviour.

The goal is not to document every word, but to define the words that matter.

### Capture Important Terms

Terms should be added when they influence requirements, business rules, user workflows, domain models, APIs, data structures or decisions.

If misunderstanding a term could lead to the wrong software, it belongs in the glossary.

### Define Terms Clearly

Definitions should be short, specific and written in plain language.

A good definition explains what the term means in the relevant context, not every possible meaning it may have elsewhere.

### Include Distinctions

Closely related terms should be distinguished from one another.

For example, if two terms appear similar but behave differently in the domain, the difference should be made explicit.

### Record Context

Some terms have different meanings in different contexts.

Where this happens, the glossary should capture the context rather than forcing a single definition that hides important differences.

### Keep It Current

The glossary should evolve as understanding changes.

Outdated definitions are dangerous because they create false confidence. Changes in terminology should be reviewed and reflected across related documents and models.

## Key Takeaways

- A glossary is a shared reference for important terms.
- It should define terms that affect understanding, decisions or behaviour.
- Definitions should be concise and context-specific.
- Similar terms should be clearly distinguished.
- The glossary must be maintained as knowledge evolves.
